# Design-sets

A design-set is the durable, versioned source of one complete look. The live forum is only ever changed by
applying a set (or rolling back to a snapshot), so any look can be recreated, compared and undone.

Location: `<repo>/design-sets/<name>/` (repo = the flarum2-ops repository root; `forum.json` → `design_sets_dir`).

## Folder layout

```
design-sets/<name>/
├── set.json          required, schema below
├── custom.less       → setting custom_less       (when "less" is set)
├── header.html       → setting custom_header     (when "header" is set)
├── footer.html       → setting custom_footer     (when "footer" is set)
├── static/           fonts/images served at /assets/design-sets/<name>/… (copied on apply)
├── images/           sources for logo / logo_dark_mode / email_logo / favicon uploads
└── screenshots/      generated by preview/screenshot (git-ignored)
design-sets/_snapshots/<id>/   automatic pre-write snapshots (git-ignored)
design-sets/gallery.html       generated comparison page
design-sets/.applied-<id>.json which set is live on one forum (one file per forum), expected values (drift)
```

## set.json

```json
{
  "name": "slate-amber",                     // = folder name, kebab-case
  "title": "Slate & Amber",
  "description": "One line for the gallery.",
  "flarum": "^2.0",
  "requires_extensions": ["fof-pages"],      // checked only; never enabled automatically
  "settings": {                              // design keys + keys of listed extensions
    "theme_primary_color": "#B45309",
    "theme_secondary_color": "#1E293B",
    "color_scheme": "auto",                  // auto | light | dark | light-hc | dark-hc
    "show_theme_selector": true,
    "theme_colored_header": true,
    "welcome_title": "Hello"                 // optional keys only change when listed
  },
  "less": "custom.less",
  "header": "header.html",
  "footer": "footer.html",
  "static": "static",
  "images": { "logo": "images/logo.png", "logo_dark_mode": "images/logo-dark.png", "favicon": null },
  "tags": { "general": { "color": "#B45309", "icon": "fas fa-comments", "description": "…" } }
}
```
(JSON has no comments; the `//` notes above are explanations only.)

### Semantics (what apply does with each field)

| Field | Present | Omitted |
|---|---|---|
| Theme keys: `theme_primary_color`, `theme_secondary_color`, `theme_colored_header`, `color_scheme`, `show_theme_selector`, `custom_less`, `custom_header`, `custom_footer` | written | **reset to Flarum's default** (colors → `#4D698E`, `custom_less` → `""`, others deleted). Switching sets is deterministic: nothing leaks from the previous set. |
| Optional keys: `forum_title`, `forum_description`, `welcome_title`, `welcome_message`, `default_route`, `show_language_selector`, `fontawesome_*` | written | untouched |
| Extension keys (`<extension-id>.<key>`) | written; the extension must be in `requires_extensions` and enabled | untouched |
| `images.<kind>` = file | uploaded (skipped only when this set uploaded the same file and that very upload is still live; a logo replaced since, e.g. in the admin UI, is re-uploaded and `doctor` reports it as drift) | untouched |
| `images.<kind>` = `null` | image removed | untouched |
| `tags.<slug>.<color/icon/description>` | patched on that tag | untouched |

Keys a set can never write: image paths (`*_path`, use `images`), `extensions_enabled`, `version`,
`custom_less_error`, `assets_dirty.*`. Protected keys (mail, maintenance, drivers, secrets) are refused in sets.

### Static files and `@@ASSET:…@@`

- Allowed in `static/`: `.woff2 .woff .ttf .otf .png .jpg .jpeg .webp .gif .svg .avif .ico`. Never PHP (nginx would execute it).
- In LESS/HTML/settings write `@@ASSET:fonts/Inter-latin.woff2@@`. Apply publishes `static/` as a new version
  folder `<forum>/public/assets/design-sets/<name>/<version>/` (`<version>` = first 8 hex chars of a sha256 over
  all static file names and contents) and replaces the placeholder with
  `/assets/design-sets/<name>/<version>/fonts/Inter-latin.woff2`. The version in the path matters: nginx serves
  fonts with a 30-day cache, so the URL must change when a file changes. Published versions are never
  overwritten.
- A set that replaces or deletes an image whose current file a rollback could not upload again (not on the local
  assets disk, or a type Flarum 2 refuses such as `.ico` from a 1.x upgrade) is blocked in `plan`.
- Only symlink-free regular files inside the set folder are published. A `static` folder outside the set, or a
  symlink to outside, is a validation error (so a shared set cannot publish e.g. `config.php` or the token).
- Placeholders inside comments are ignored; a placeholder pointing to a missing file is a validation error.

### Images

Flarum 2 accepts jpeg/png/gif/webp/bmp up to 2 MB and 24 megapixels (no SVG, no ICO). It rescales:
logo and dark logo to 60 px height (WebP, animated → GIF; small images are upscaled, so give ≥120 px height),
email logo down to ≤120×1120 px (PNG), favicon to fit 64×64 keeping the aspect ratio (PNG). Every upload
gets a new random file name and deletes the previous file. A normal logo upload also writes an email-safe
copy (`logo_email_copy_*`). **The dark-mode logo is only rendered when a normal logo exists**
(`views/frontend/forum.blade.php`: it sits inside `@if ($forum['logoUrl'])`), so a set that adds
`logo_dark_mode` also needs `logo` (validation and the upload dry run warn about this).

## Lifecycle

```
new / export ─► edit ─► validate ─► diff ─► preview (snapshot→apply→screenshots→rollback) ─► gallery
                                              │
                                              └─► apply (snapshot→write→verify; auto-rollback on failure) ─► rollback
```

### apply, step by step
1. Validate + admin check; take the write lock (`design-sets/.lock`).
2. Snapshot (settings incl. every enabled extension's keys, the served image files, tag styling, marker).
3. Publish `static/` as a new version folder (adds files only).
4. POST `custom_less` alone. On 422 no other setting has been written yet (the static version folder from step 3
   exists, unreferenced); Flarum keeps the old `custom_less` but sets `custom_less_error`. The automatic rollback
   re-saves the old value, which clears the flag. With `--no-auto-rollback` nothing is cleaned up: run
   `designset rollback <snapshot>` yourself, or `custom_less` stays dropped on every compile.
5. POST the remaining settings; DELETE omitted theme keys that are not CSS defaults.
6. Upload/delete images; PATCH tags.
7. Clear the cache only if a reset (or a null value) touched a CSS key or `fontawesome_*` changed (saving
   custom_less/colors rebuilds CSS by itself; a deleted key does not).
8. Verify: read back every key, `custom_less_error` must be empty, health (services, root/API/own stylesheets 200).
   New ERROR lines in `storage/logs` are reported as warnings (`logErrors`), never a reason to roll back: on a busy
   forum they cannot be told apart from errors of other requests. Read them before you call the apply a success.
9. Remove static version folders of this set that nothing references any more; write the forum's `.applied-<id>.json` marker; return the
   snapshot id, rollback command and an operations.md entry.

Any failure in 3–9 triggers an automatic rollback to the snapshot from step 2 and reports both results. The automatic
rollback (also the one ending every preview) restores only what this apply wrote: the keys it set or reset, the
image kinds and tags the set names. Changes others made meanwhile (admin UI, extensions) stay. A manual
`designset rollback` restores everything the snapshot recorded.
Preview and a failed apply only add a version folder; they never remove or overwrite one, so the LESS that a
rollback restores still finds its files. After a *successful* apply, version folders of that set that neither
the new state nor any snapshot references are removed.

### rollback
Restores each key to exactly its snapshot state: value → POST, NULL → POST null, absent → DELETE; re-uploads
or deletes images whose presence changed; restores tag styling; re-saves `custom_less` if `custom_less_error`
is set; clears the cache when a CSS key was deleted; restores the marker; then re-compares (a re-uploaded image gets a new
file name; it counts as restored when it is the file this snapshot's rollback uploaded, recorded in `restored.json`). A failing step does not stop the others: everything restorable is restored and the
failures are reported together at the end (an error, so the operator sees what is left). Only keys and extension prefixes
the snapshot recorded are compared, so settings of an extension enabled later are left alone. Before writing, a
rollback snapshots the current state (`before-rollback`, returned as `undo`), so it can itself be undone.
`rollback` without an id uses this forum's newest *pre-write* snapshot (`before-…`: apply, settings or image
write), never a preview (it rolled itself back), export, manual or rollback snapshot. Protected keys (mail,
maintenance, drivers) are restored only with `--allow-protected` / `allowProtected`; the dry run lists them as
`skippedProtected`. Snapshots and the applied-set marker belong to the forum they were taken of: restoring a
snapshot of another forum (shared design-sets folder) needs `--other-forum` / `allowOtherForum` and the
owner's explicit approval. Confirm with the id the dry run shows (`confirmWith`):
another write in between creates a newer default.

### Snapshots
Every confirmed write takes one (`design-sets/_snapshots/<time>-<reason>/`: `snapshot.json`, copies of the image
files, and `restored.json` once a rollback re-uploaded them), so they accumulate. Nothing deletes them
automatically. `designset prune-snapshots [--keep 20]` (dry run first) removes all but the newest N; the snapshot of
the applied set is always kept. `doctor` hints at it above 50 snapshots. A rollback to the same snapshot twice does
not upload its images again. Restoring an image means uploading it again, and Flarum re-encodes every upload
(logo: 60 px WebP): when the live image was the applied set's own upload and its source file is unchanged, the
rollback uploads that source file; otherwise it uploads the snapshot copy, which costs one re-encode.

### preview
Pre-flight (can the screenshot helper start a browser? if not, nothing is applied) → snapshot → apply →
screenshots → rollback, always (also on failure, on a helper timeout and on Ctrl+C/SIGTERM). Pages: `/`, `/all`, the first discussion,
`/tags`; schemes: light/dark (browser emulation) plus light-hc/dark-hc (data-theme) when `color_scheme` is
`auto`, else the forced scheme; viewports 1440 and 390. Each shot records console errors, failed requests and
whether Flarum's loading-error fallback is visible. Visitors briefly see the previewed design while it runs.

### Drift
The marker (`.applied-<id>.json`, one per forum) stores the expected theme values. `doctor` reports drift when the live values differ
(someone used the admin UI). Before overwriting drifted changes, `designset export <new-name>` to keep them.

## Good set hygiene
- One look per set; name sets by look (`slate-amber`, `nordic-night`), not by date.
- Keep `custom.less` structured: fonts → palette variables → CSS custom properties → components (see template).
- Keep copy (headlines, footer text) in HTML or variables, not hard-coded in selectors.
- Commit sets to the repo; snapshots and screenshots stay git-ignored.
